What this tells you

  1. The mobile path now reaches active on its own. POST /api/v1/me/photos exists, needs only the profile:write ability a pending token carries, and recomputes completion after every upload and delete — so a member who signs up in the app can fill every checklist item. Diagram 2.
  2. Photos, account deletion and “who liked you” all have endpoints. Six routes were added; the API surface is 39 endpoints, seven public. Deletion is a soft-delete plus anonymisation, on purpose — the moderation record survives it. Diagram 12.
  3. Only some notifications are wired. match.new, message.new, and the four billing templates are sent. appeal.received, appeal.decided, verification.approved, verification.rejected, verification.prompt, likes.waiting, match.silent_nudge and profile.incomplete exist only as editable templates. Enforcement records notified_user = true without sending anything. Diagram 10.
  4. The payment flow is web-only. Stripe Checkout and Razorpay Payment Links are hosted, offsite pages. Apple and Google require in-app purchase for digital subscriptions inside a native app, so this flow cannot be used there as-is. Diagram 8.
  5. No staff path closes a conversation. The only triggers are a block (either direction) or an unmatch (web or API). The close_conversations permission was removed because nothing checked it. Diagram 5.
  6. One API write still does not recompute profile completion. PATCH /me (city) saves without calling ProfileCompletion::refresh(); the city counts on the next write that does. PUT /me/interests now refreshes, as the website always did. Diagram 2.
  7. Only suspensions self-clear on the next request. Expired shadow bans and feature limits wait for the five-minute scheduler. Diagram 11.
  8. Email and push are queued. Without a running worker they are never delivered and nothing fails visibly. Diagram 10.

1Three audiences, four guards

Who can be signed in, on what, against which table

Two populations, two tables. Members are app_users, reachable through a browser session on the member guard or a Sanctum token on the api guard. Staff are users, only ever on the web guard. Each population has its own password-reset broker and token table. Being signed in on one guard grants nothing on another: a member's browser session does not authenticate API calls, and neither a member session nor a member token opens anything under /admin.

The appuser.active and member.active middleware are what turn a ban into a locked door: they read the mirror columns on app_users (diagram 6) on every request. Staff get the same treatment from staff.active, which also runs on Livewire updates so a suspended moderator loses an open tab, not just the next login.

2Member lifecycle

From visitor to active — from either client

Every account starts pending — that is the column default, and neither registration path changes it. Promotion to active happens in exactly one place, ProfileCompletion::refresh(), when at least half of the eight checklist items are done. Until then a mobile token carries only profile:read, profile:write and verify, so the deck, swipes, messages and reports are refused by the ability: middleware.

Both clients can now fill every item. The mobile API's POST /me/photos goes through the same MemberPhotoStore the website uses — the GD re-encode that strips EXIF and neutralises hostile files is the security control, and there is one path through it — and recomputes completion after every upload and delete. It needs only profile:write, which a pending token carries, so a member who signs up in the app is never stuck. One write still does not recompute: PATCH /me (city); the city counts on the next write that does.

Leaving active — and what an account returns to

Leaving active goes one of two ways. The member can deactivate themselves. Everything else is an enforcement (diagram 6), and when it ends — by expiry, a lift, or an overturned appeal — the account returns to the status it held before: a pending or deactivated account is not promoted by a suspension running out. A permanent or device ban has no expiry, so only a lift or an appeal ends it.

3Discovery deck

Every exclusion, in the order the query applies them

The exclusions are the safety rules of the product expressed as SQL. A shadow ban has no code of its own — it is simply that shadow_banned is not active, and this is the only place that takes effect. Blocks are checked in both directions, so blocking someone also removes you from their deck.

Geography is one of three scopes. A radius wins whenever it can be computed: a bounding box over the coordinate index throws away nearly everyone cheaply, and the haversine trims the square's corners to a circle over the few rows left. Members with no coordinates cannot satisfy a radius and are excluded from one. Random order is a random pivot on the primary key walked in index order, then a PHP shuffle of the handful kept — not ORDER BY RAND(), which sorted every candidate on every swipe.

The two clients differ in one thing: the website's withFallback() widens to anywhere when the local area is empty and says so; the mobile API's for() returns the empty deck, so existing app clients see no change in behaviour.

4Swipe → match → conversation

One transaction, from a like to an open thread

A match is derived, never asserted: it exists only when a like meets a like already on the other side, and the unique index on the canonically-ordered pair means the same two people can never match twice. The conversation and its participant rows are created in the same transaction, because a conversation without participants belongs to nobody and both people would be refused their own thread.

The daily like limit is a product rule, not burst protection, so it lives here rather than in the rate limiter. It is counted and enforced inside the transaction behind a lock on the member's own row, so concurrent requests cannot all read the same total and walk past the cap. A re-swipe on someone already decided about replaces the earlier row — that is deliberate, and it is how a pass can later become a like.

5Messaging and safety

Conversation state: what closes a thread

A thread has two states and three ways to leave the first. All three funnel through MatchActions, which owns the pair “end the match, close the conversation” so a caller cannot write one row and forget the other — the API used to. Blocking does not delete anything; it marks the match blocked rather than unmatched, so the moderation queue can tell the two apart. There is no staff action that closes a conversation.

Sending a message: the three guards, one service for both clients

Three separate rules, answered in one place. They used to live in the website's Livewire component, which meant the website enforced them and the mobile API did not — a blocked member could keep messaging over the API. 6Report → case → enforcement ladder

From a report to a ban, and what is written where

Reports become cases, and cases are what moderators work. CaseAggregator folds every report about one member into that member's single open case under a row lock, so ten reports in a minute are one item in the queue, not ten. Severity comes from the category — reporters mislabel — and a new report can only raise it. The SLA clock is set from severity when the case opens.

Enforcement is one write path for the console and for automation alike, which is why actor_type is a parameter. In a single transaction it appends a moderation action, creates the ban row for the five steps that carry one, and writes the mirror columns on app_users that the middleware in diagram 1 reads. A shadow ban cannot be created without a review date — it is invisible to the member, so nothing but a calendar entry would ever prompt anyone to revisit it. Moderation actions are append-only at the model level: an update or delete throws.

Appeals, lifts and expiry: reversing without erasing

An appeal records who made the original decision and is routed away from them twice — at assignment and again at decision — so the process cannot rubber-stamp its own work. An overturn actually lifts the ban; an appeals process that records a verdict without changing anything would be theatre. A lift is a new action linked back to the one it reverses, never an edit, and the scheduler's expiry uses the same path with actor_type = automation so the audit trail does not put a person's name on something the clock did.

7Message content reveal

Why bodies are hidden, and what it takes to read one

Privacy here is structural, not procedural. Because body is in the model's $hidden array, no list, resource or accidental toArray() can leak message text — it has to be asked for. Asking means holding the permission, choosing one of four fixed reasons, and writing a justification, and the ask produces two immutable records: one in the dedicated access log and one in the general audit log flagged as sensitive. The access-audit screen exists so that staff reveals are themselves reviewable.

8Subscription and payment

Two confirmations, one fulfilment

A payment is confirmed up to three times — by the return page, by the webhook, and again when the gateway retries the webhook — and the member must end up with exactly one subscription. Both confirmations converge on fulfil(), which re-reads the order under a row lock and does nothing if it is already paid. Webhooks are deduplicated by the gateway's own event id, but a row counts as a duplicate only once processed_at is set: if fulfilment fails, the retry is not mistaken for a repeat and is allowed to finish the job.

Renewing early adds to the time left rather than replacing it. Expiry is the scheduler's job; the mirror is cleared only when the lapsed row is still the plan the member is on, because a renewal may already have replaced it. None of this applies inside a native mobile app: the stores require in-app purchase for digital subscriptions, which this web-hosted checkout does not use.

9Verification

A code the server remembers, a photo the server keeps private

The gesture code is what stops a photograph of a photograph, and that only holds if the server remembers what it issued. It is generated server-side, held against the member for ten minutes, compared with a constant-time check, and consumed on use — a client cannot choose its own. Selfies are identity data: they go to a private disk and are served to staff only through a signed URL that expires, behind the verifications permission, with every view written to the sensitive audit log.

Approval sets the member's status and verified_at in the same transaction. A submission that a reviewer suspects involves a minor is escalated into a separate queue that staff without its permission cannot even see, and inside that queue approval is not offered — only rejection or further escalation.

10Notifications

What fires today, and what is only a template

Every member-facing message takes its words from a template the operator can edit, and every send is logged so “did they get it?” is answerable from the console. Six things are actually sent; nine templates are editable text with no code behind them. Enforcement is the awkward one — the console records that the member was notified, and no notification exists.

Both channels are queued. The email log is written as queued and only settled to sent or failed when the mail is handed over, because writing sent at dispatch would be a lie the moment a worker stops. Push is a job that re-reads the member before sending, so a ban applied in the meantime is respected — but a shadow ban is deliberately not, since an account that suddenly goes quiet is a tell.

11Scheduler

One cron entry, three commands, and what happens without them

Everything the clock owns hangs off one cron line. Restrictions and plans end on time, renewal warnings go out at the right hour, and approved campaigns leave when scheduled. The product degrades gracefully without it: a suspension clears itself the next time the member does anything, because both member-facing middleware check suspended_until — but that is the only self-clearing case. A lapsed shadow ban or feature limit, and every renewal reminder and campaign, waits for the scheduler. The commands themselves now mostly dispatch jobs, so a queue worker is the other process that has to be running.

12API surface map

The middleware stack every authenticated call passes through

Thirty-nine endpoints, seven public. Everything else passes the same four gates before a route-specific ability or throttle is considered. Limits are read from settings so they can be tightened during an incident without a deploy; accounts under 24 hours old get half the swipe and message allowances. Responses always go through a Resource — that is where risk scores, internal notes and shadow-ban state would otherwise leak, and MeResource maps shadow_banned to active on the way out.
